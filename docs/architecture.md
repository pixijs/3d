# Architecture

Where each cross-file contract starts. The named entry point is where to read on.

- **Backends.** WebGPU and WebGL2 code lives in `src/core/gpu/` and `src/core/gl/`. Shared code imports them as types only, which lint enforces, and reaches a pipe through `View3DPipe`. A difference between the two pipes is deliberate when its JSDoc says so, as with `rebaseIndices` and culling.
- **Layout.** `src/core` is the renderer side: batcher, stores, render graph and passes, shader bits, and culling. `src/scene` holds the display objects, cameras in `src/scene/cameras` and lights in `src/scene/lights`, where `Light.ts` also declares `LightShadow`. Post-processing is split: `Pass3D`, `PostEffect`, `FullscreenPass` and `OutputPass` are in `src/post-processing`, and the effects and extra passes are in `src/extras/post-processing`. `src/extras` holds the opt-in features, and one feature can span its folders, as portals span `src/extras/materials/portal` and `src/extras/post-processing/passes/portal`. Lint is `oxlint.config.ts`, with the custom rules in `scripts/lint/rules/`.
- **A frame.** `View3DPipeGpu.execute` and `View3DPipeGl.execute` run one view's frame top to bottom: `updateView3DScene`, store uploads, lights and globals, then the render graph. `prepareCamera` builds each camera once per frame for the target it draws into. `CameraData.set` edits only the camera's GPU copy of its matrices: `Camera3D.jitter`, turned from pixels into NDC against the GPU viewport in `syncFromCamera`, then the target's Y flip, then the WebGPU depth remap. So the camera's own `projection`, `viewProjection` and `frustum`, which culling and picking read, never carry the jitter. `syncFromCamera` also keeps the camera's own `viewProjection` from its previous render and turns it into a GPU matrix the same way, with this render's jitter and target (`toGpuMatrix`), as `uPreviousViewProjectionMatrix` for any temporal effect: the jitter cancels when a shader subtracts the two positions. `Camera3D.resetHistory` drops that history for a camera cut, so the next render reads no motion.
- **Material to shader.** A material lists its bits in `getPrimaryDescriptor`. The material system's `ensureMaterial` wraps them in the mesh's and the view's bits and compiles the result into the mesh's `_passCache`; a pass with its own shader compiles it in `RenderPass.onRenderableDirty`. `bit.name` is the shader cache identity. A bit lists the bits it needs in `requires`; the shader compiler adds each one once, ahead of the first bit that asked, and returns the full list as `bits`. A bit declares the colour outputs it writes in `outputs` and writes them through the `outputs` local, as the material templates write `outputs.color`. `ShaderDescriptor.outputLocations` lists the ones that reach the GPU, each at its index in the list as its location; a declared output the list leaves out stays in the internal `Outputs` struct and the shader compiler drops it. `wgslFragmentOutputsPlugin` and `glslFragmentOutputsPlugin` generate both, and only for templates that have the output slots.
- **Batching.** A pass sorts its renderables by `_sortKey`, which `updateMesh3DKeys` lays out as pipeline, texture set, geometry, then material, and `Mesh3DBatcher` (WebGPU) or `Mesh3DBatcherGl` (WebGL) walks that order once. A run is a stretch of rows with one batch key and one texture set (`BaseMaterial3D._textureSetId`, compared where the material changes). On WebGPU it draws a command each time its material changes, bound to the material's own group (`BaseMaterial3D._getBindGroup`), until that would come to more than `MERGE_THRESHOLD` commands. Past that it draws as one merged command with the pass entry's `mergedShader`, each instance reading its material row from the store's texture. On WebGL every run in a pass that binds the material draws merged from its first row, since a direct draw there costs a uniform-block rebind per draw. A pass binds the mesh's material at group 2 only when it draws with the material's own shader, which needs a material's bit (`RenderPassBit.MATERIAL_PASS_MASK`) and no shader in its `descriptor`. `ForwardRenderPass` works that out once, as `bindsMaterial`. Every other pass, such as shadow, outline, or any pass with a shader of its own, draws a shader compiled without the material bindings, binds no material there, and its runs break on the batch key alone.
- **Render graph.** `createDefaultGraph3D` (`src/scene/utils/`) declares the default passes in run order, and `RenderGraph` compiles and runs them. Each pass declares what it reads and writes in `setup(builder)`. A pass whose work leaves the graph, such as a readback, calls `PassBuilder.sideEffect` so the cull keeps it. A pass that binds a graph texture itself, such as raw WebGPU compute, gets it in `render` from `RenderGraph.getTexture`, which throws by name outside the texture's lifetime. Every transient is stored the way the view's default target is; `RenderGraph.execute` records that target's front-face inversion as `RenderSession.defaultFrontFaceInverted`, and `FullscreenPass` compares its bound target with it to flip V, so a copy lands upright in a texture the app imported. `View3DGCRegistry` relays pixi's `TexturePool` `evict` event to each view's graph, which puts the placeholders back in every transient binding it made. `RenderGraph.destroy` does the same before it destroys its passes.
- **Scene resolution.** `View3D.resolution` sets the texels the scene draws at. `View3D._ensureInitialized` requests composite mode while that differs from the target's, rebuilds the graph when the request changes unless it already composites and composite mode is now requested, and hands the graph the number as `RenderGraph.resolution` every frame. Every graph texture whose `resolution` is `'inherit'` (the scene pair, the opaque copies, the scene outputs, effect textures) follows it, so a scene pass's attachments stay one size and only the last draw onto the screen works at the view's full size. `prepareCamera` takes `uViewportUVScale` from `RenderGraph.sceneViewport` and `cameraFrameToPhysicalViewport` places insets at the scene's resolution, not the screen's. The `OutputPass` that ends a composite view is a `FullscreenPass`, whose input clamp keeps the stretched draw half a texel inside the scene. A post effect's `texel()` follows the pass's target, and `viewTexel()` is one physical pixel of the view on screen, for sizes that must look the same at any resolution and place in the chain.
- **Tone curve.** It runs at the end of the material and sky shaders, or once in an `OutputPass`, and `RenderGraph.sceneIsLinear` decides which. `View3D._ensureInitialized` reads it after each graph build and sets `_toneMappingBit`: the view's curve, which the material systems and `BackgroundPass` end their shaders with, or `null` when the scene holds linear light. `createDefaultGraph3D` makes the scene `rgba16float` while a `'beforeToneMapping'` effect is enabled and adds the `OutputPass` after the last of them. A colour texture created without a format takes the scene's format (`RenderGraph.createColor`), so effect textures and the opaque copy follow it, apart from bloom's blur levels, which take `floatRgbFormat` in a linear scene. In a linear scene, a camera with a render texture draws in the scene's format too (`RenderGraph._cameraTargetFormat`). When its texture has another format, `View3DPipe.outputColor` writes the picture into it through `ColorOutputDraw`, which ends its shader with `toneOutputBits` as `OutputPass` does. Those bits apply the view's curve and the output dither when the texture's format isn't linear, and nothing when it is. A shader that reads the scene colour back as light picks `decodeToLinearBit` from whether `_toneMappingBit` is set, as transmission does.
- **Scene outputs.** A `SceneOutput` is a texture the scene draw writes besides its colour, declared as a plain object and known by its name, as a `ShaderBit` is: `assertSceneOutput` checks one on first sight and `sameSceneOutput` lets two copies with one name and the same content count as one. Core defines none; `velocityOutput` and `normalOutput` live in extras (`src/extras/scene-outputs`), built the way an app builds its own, and `MotionBlurEffect` and `SsaoEffect` (with `sceneNormals`) read them. A pass lists the outputs it needs in `Pass3D.requiredOutputs`; `createDefaultGraph3D` collects them from its `passes`, adds any `options.sceneOutputs` (`collectSceneOutputs`) and goes composite, and `RenderGraph` creates a texture per output, at the scene colour's size and sample count, behind `getSceneOutput`; `hasSceneOutput` lets a pass use one only when the view has it. Each scene pass attaches them after its colour (`RenderPass.attachedOutputs`, `_writeTarget`), and gives its materials the bit each output names for that pass (`RenderPass.materialBits`, from `materialBitsFor`). A material on the engine's template compiles against its pass's output locations and, when the pass attaches outputs, its `materialBits` (`addPassMaterialBits`, through `View3D.passByBit`); any material's own bits can write an output by name. On an antialiased canvas the outputs are multisampled with the scene and resolved with it, by averaging; `createDefaultGraph3D` draws the scene single-sample while any output's format can't be resolved that way (`isResolvableFormat`: integers, 32-bit floats, and `rgba8unorm` on WebGL). The graph resolves a multisampled colour after its last writer, and also after an earlier writer when a pass samples it before the next write (`AddedPass.resolvesColor`), so an `'afterOpaque'` reader sees this frame's values on WebGL too. On a target with several attachments each one clears or loads on its own, and takes its output's clear value (`RenderGraph._setColorAttachments`); `assertColorAttachmentLimits` checks the GPU's caps on the first `resolve` after each compile, before anything is acquired. Mistakes that would reach the GPU as raw errors throw first: `assertOutputName` (a name a shader field can't carry) and `assertSceneOutput` (a blended pass's float output written as less than a `vec4`). `SceneOutput` and `velocityOutput` have the rules: who writes an output, blending, clear values, limits, and velocity's units and sign.
- **Culling.** `View3D`'s `cull` option, or a `BatchedMesh3D`'s own, sets how a batch drops instances outside the camera: `'off'`, `'cpu'` or `'gpu'`. `resolveCullProducer` (`src/core/cull.ts`) turns that into what each pass uses, falling back to `'cpu'` where the pass can't compact on the GPU. On WebGPU, `src/core/gpu/cull.ts` writes a batch's survivors into its `CullResult`, which the pass holds in `CullResults`, from a compute pass (`produceVisibilityCompaction`) or a JavaScript frustum test (`produceCpuCompaction`). On WebGL, `Mesh3DBatcherGl` culls while it compacts its index texture.
- **Invalidation.** A reallocated shared store (`bufferVersion`, checked in `detectSharedCacheInvalidation`) rebuilds every batch's draw commands. A batch's `invalidateDrawCaches` rebuilds its commands, and `invalidateBundleCaches` only re-records its bundles. A mesh's `_batchDirty` rebuilds its shader and keys, and `_storeDirty` its store row. Raise them through `Mesh3D._markBatchDirty` and `_markStoreDirty`, which also queue the mesh, because `updateView3DScene` visits only queued meshes. A change on a shared geometry or material reaches its meshes through the resource's `_meshes` list. A material variant change bumps the material's `_descriptorDirtyId`, and each mesh keeps its own last-seen value, never a flag the first reader clears. Anything that bumps `drawDirtyId` or `bundleDirtyId` every frame turns the batches it touches into per-frame rebuilds. A pass sorted by distance also rebuilds when its sort bumps the view's `orderDirtyId` (`DrawList.isOrderStale`), so anything that bumps that every frame turns the pass into a per-frame rebuild too.
- **Membership edits.** In a pass sorted by key, each draw command owns its members once it is built: `DrawList` keeps the command of every store row, and the list's records hold the rows grouped by command. A mesh joining, leaving or changing kind edits those (`DrawList.add`, `remove`, `move`), and `DrawList.applyEdits`, at the end of the scene update, gives each joiner the command that draws its kind, compared exactly, or a tail command of its own after the built ones, then lays the records out again from the first command that changed. The sorted view is only sorted again by a rebuild. `DrawList.applyEdits`, `isDrawStale` and `nextBuild` list what rebuilds a list instead of editing it.
- **Resource events.** Meshes and materials never listen to a pixi resource; draw lists do. A list adds one `change` listener to each buffer and texture source a build records, and one `styleChange` listener to each texture source. `endBuild` removes them from a resource the build stopped recording, and a tail command holds its own captures, counted on the capture, and gives them back when its last member leaves (`DrawCommandList.releaseTail`). A material's bind groups hold their resources unwatched. Only `BaseMaterial3D._refreshTextureBindings` changes their textures and styles. A rebuild's walk runs it as it meets the material, but only when `textureDirtyId` moved; a slot swap drops the material's groups instead, and the next ones are built from its current slots. One listener per object on a shared resource makes teardown N², because pixi's emitter rebuilds its listener list on every removal. Mesh or material code that needs to see a resource change joins the draw list's captures and doesn't add its own listener. The exception is `Sprite3D`, which follows pixi's 2D `Sprite`: a sprite listens to its texture's `update` only when the texture is `dynamic`.
- **Membership.** Visibility never changes which passes a mesh is in; removing the mesh or changing its `renderPassMask` does.
- **Ownership.** Per-renderer data lives in `view3d._gpuData[renderer.uid]`, and views enroll in `View3DGCRegistry`. `CODING_STANDARDS.md` has the `destroy()`/`unload()` contract.
- **Caches.** A new variant input joins the key of every cache it affects; start from the material systems' `compileShader` and `src/core/batcher/updateMesh3DKeys.ts`. Caches keyed by texture uid clear only on destroy.
- **Entry points.** Extensions register only in `init.ts` files, which `package.json` lists in `sideEffects`. `scripts/build/index.mts` generates the folder barrels. `src/core/gl` and `src/core/gpu` get their own, which their `init.ts` re-exports as `@pixi/3d/webgl` and `@pixi/3d/webgpu`, and no other barrel exports them, so each backend stays in the lazy chunk its `init.ts` fronts; `npm run test:bundle` checks the split with rolldown and esbuild.
